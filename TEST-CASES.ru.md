# Проверка LinkedIn Sales Navigator Connector

Версия набора: 2026-10-01. Объект: локальный MCP-коннектор из этого репозитория.

90 тест-кейсов в 9 наборах. Цель — проверить заявленные возможности и обнаружить расхождения между запросом, ответом коннектора и фактическим состоянием LinkedIn/Sales Navigator. Это спецификация для прогона, а не отчёт о выполнении живых тестов.

Основания: `README.md`, схемы MCP, браузерный адаптер, сервис отправок, журнал операций и локальные диагностические снимки от 2026-10-01. В ходе подготовки выполнены существующие автоматические тесты: **8 из 8 прошли**. Они проверяют схемы, журнал, часть логики сообщений и регистрацию MCP-инструментов; работа с живым интерфейсом ими не подтверждена.

## Как выполнять и оценивать

- **P0** — неверный адресат, повторная отправка, ложное подтверждение успеха, нарушение preview или потеря существенной части результатов. Блокирует использование соответствующей операции.
- **P1** — основная функция, точность данных, фильтры, доступ и диагностика.
- **P2** — дополнительные варианты интерфейса и восстановления.
- **PASS / FAIL / BLOCKED / NOT RUN / N/A** — статусы прогона. Все 90 кейсов исходно имеют статус **NOT RUN**. Для BLOCKED и N/A обязательна причина; они не считаются PASS.

Ожидаемый результат в таблицах — критерий приёмки. Некоторые критерии намеренно строже текущей реализации: они нужны, чтобы обнаружить дефект, а не закрепить его как норму. Там, где не согласован точный формат нового ответа, указан обязательный смысл результата. Ошибку проверять через MCP: `isError=true`, `ok=false` и содержательный код/описание; ошибку схемы может вернуть сам MCP SDK до входа в обработчик.

Каждый вариант, перечисленный в строке, запускать отдельно с суффиксом, например `FLT-08/51-200`. В отчёте не объединять PASS одного варианта с FAIL другого.

### Подготовка

1. Зафиксировать дату, версию кода, Chrome/Node, язык самого LinkedIn, тип доступа Sales Navigator, размеры окна, масштаб и режим `review/execute`. `LINKEDIN_LOCALE` сам по себе не доказывает язык интерфейса аккаунта.
2. Для базового прогона использовать английский интерфейс и размер окна 1440×1000. Другие языки и размеры проверяются отдельно.
3. Работать с одним процессом коннектора и его отдельным браузерным профилем. CLI и MCP не должны одновременно открывать один профиль. Исключение — специальный кейс SES-07.
4. Начать с `review`. Для MSG/CON с реальной отправкой нужны заранее согласованные тестовые получатели и `execute`. Приглашения изменяют связь аккаунтов: следующий кейс выполняется на другом подходящем получателе либо получает BLOCKED до восстановления предусловий.
5. Зафиксировать доступные в этом аккаунте подписи фильтров и значения. Названия отраслей/компаний брать из реальных подсказок. Не подменять ожидаемое значение похожим, если нужного нет.
6. Перед базовыми поисками вручную убрать и фильтры, и ключевые слова; отдельно проверить отсутствие скрытых Include/Exclude. Для кейсов очистки, напротив, специально оставить предыдущее состояние.
7. Сбои после клика, конкурентные отправки, ошибки диска и длительные задержки воспроизводить сначала на локальном стенде с подменяемым браузерным адаптером/страницей и отдельной тестовой БД. Такой стенд сейчас не входит в репозиторий; без него соответствующий вариант BLOCKED. Результат стенда не заменяет проверку совместимости с живым UI.

### Общая процедура сверки с UI

1. Выполнить действие вручную на том же аккаунте, записать выбранные значения, режим Include/Exclude, состояние страницы, контрольные поля и URL. Затем вернуть исходное состояние, нужное для кейса.
2. Вызвать инструмент с указанными аргументами. Сохранить исходный запрос и полный ответ, а не только пересказ агента.
3. Проверить состояние браузера после вызова: нужная страница, выбранные значения, завершение загрузки, адресат и итог действия.
4. Сравнить JSON с UI. `ok=true`, непустой массив и `appliedFilters` сами по себе не означают PASS.
5. Для поиска сверять каждую полученную карточку с карточкой соответствующей страницы. Выдача может меняться: изменение порядка само по себе не дефект; повторить в коротком интервале и сохранить доказательства стабильного расхождения.
6. Для отправки проверить адресата и исходящее сообщение/приглашение после повторного открытия страницы. Закрытие окна и очистка поля сами по себе не подтверждают отправку.

## 1. Сессия и доступ — SES

Общая операция: `linkedin_session_status({})`; для проверки рабочей функции — `linkedin_search_people({"filters":{},"limit":5})`.

| ID | Приоритет | Предусловия и шаги | Ожидаемый результат |
|---|---|---|---|
| SES-01 | P1 | На отдельном новом профиле без входа вызвать статус, затем поиск. | Статус `auth_required`, доступ `false`; поиск возвращает `AUTH_REQUIRED`, а не пустую успешную выдачу. |
| SES-02 | P1 | Войти вручную, открыть рабочий Sales Navigator, вызвать статус и поиск с доступным фильтром. | `authenticated`, доступ `true`, режим совпадает с настройкой; поиск действительно работает. |
| SES-03 | P1 | После успешного входа корректно закрыть процесс, запустить снова и повторить SES-02. | Сохранённая сессия используется; если LinkedIn сам отозвал её, это явно определяется. Нет ложного `authenticated` по одному URL. |
| SES-04 | P1 | Аккаунт вошёл в LinkedIn, но доступ к Sales Navigator отсутствует/показывается предложение подписки. Вызвать статус и поиск. | Доступ `false`; поиск объясняет отсутствие доступа и не выдаёт страницу подписки за результат. |
| SES-05 | P1 | Использовать уже возникшую проверку аккаунта или её локальную модель. Проверить статус и поиск; после ручного прохождения повторить. | `challenge_required`/`CHALLENGE_REQUIRED`, работа останавливается на проверке; после её завершения следующий вызов восстанавливается. Отдельно проверить проверку во время поиска. |
| SES-06 | P1 | Оставить активную вкладку на обычном `/in/` или ленте у аккаунта с действующим Sales Navigator. Вызвать статус. | Доступ оценивается корректно либо явно указан как непроверенный. Текущая вкладка вне `/sales/` не является доказательством отсутствия подписки. |
| SES-07 | P1 | При работающем тестовом коннекторе запустить второй с тем же профилем; остановить только второй. Повторить поиск первым. | Второй сообщает о занятом профиле; первый продолжает работу. Нет повреждения профиля/журнала и незаметного переключения аккаунта. |
| SES-08 | P1 | После рабочего поиска выйти из аккаунта или воспроизвести истечение сессии; запросить профиль. | `AUTH_REQUIRED`, без данных другого экрана/предыдущего человека. После входа новый запрос выполняется. |

## 2. Поиск и фильтры — FLT

Инструмент: `linkedin_search_people`. По умолчанию `limit=5`. Каждый кейс включает сверку выбранных значений в UI и состава `appliedFilters`.

| ID | Приоритет | Предусловия и шаги | Ожидаемый результат |
|---|---|---|---|
| FLT-01 | P1 | На чистом поиске отправить `{"filters":{},"limit":5}`. | Результат совпадает с поведением пустого ручного поиска. Если UI требует сначала задать условие, коннектор сообщает это явно; экран `Apply filters to find leads` не считается подтверждённым нулём результатов. |
| FLT-02 | P1 | Отдельно искать `keywords="B2B SaaS"` и `keywords="русский"`. | В поле точный текст, запрос применён, выдача обновилась. Кириллица не повреждена; глобальное поле с ролью combobox находится корректно. |
| FLT-03 | P1 | Передать `currentTitles=["Founder","CEO"]`; сравнить с ручным выбором этих двух значений. | Оба значения действительно выбраны и не заменяют друг друга. Семантика объединения совпадает с ручным UI; если нужны иные канонические подписи, несоответствие явно зафиксировано. |
| FLT-04 | P1 | Передать доступную прошлую должность в `pastTitles`; найти соответствующий фильтр вручную. | При наличии фильтра выбирается прошлая, а не текущая должность. При отсутствии — `FILTER_UNAVAILABLE` с указанием `pastTitles`, без успешной нефильтрованной выдачи. |
| FLT-05 | P1 | На новом и на уже заполненном поиске передать `geographies=["Argentina"]`. | В поле вводится полное `Argentina`; выбрана именно страна через Include; после закрытия подсказок выбранное значение сохраняется. |
| FLT-06 | P1 | Передать две географии из реальных подсказок, например Argentina и Vietnam; отдельно выбрать город с похожим названием. | Все запрошенные географии присутствуют. Страна не заменяется провинцией/городом; ни одно значение не попадает в Exclude. |
| FLT-07 | P1 | Передать `industries=[I1]`, затем два доступных значения отраслей. | Выбраны точные варианты из справочника; выдача соответствует ручному выбору. Текст из другой части страницы не принимается за пункт фильтра. |
| FLT-08 | P1 | Для каждого из 8 допустимых `companyHeadcounts` выполнить отдельный поиск; затем выбрать два диапазона вместе. | `1-10`, `11-50`, `51-200`, `201-500`, `501-1000`, `1001-5000`, `5001-10000`, `10001+` сопоставлены с реальными подписями UI, включая пробелы/разделители/знак `+`. Нет молчаливого пропуска диапазона. |
| FLT-09 | P1 | По очереди передать `connectionDegrees=["1st"]`, `["2nd"]`, `["3rd+"]`, затем два значения. | Выбраны соответствующие степени связи; варианты вроде `3rd degree+` корректно сопоставляются либо возвращается явное несоответствие. |
| FLT-10 | P1 | Передать `currentCompanies=[C1]`; отдельно проверить одинаковые/похожие названия компаний. | Выбрана нужная компания. Если строка неоднозначна и интерфейс не позволяет надёжно различить компании, нет произвольного выбора первого совпадения. |
| FLT-11 | P1 | Применить keywords + currentTitles + geographies + companyHeadcounts + connectionDegrees из подтверждённых доступных значений. | Все условия остаются выбранными после последнего шага; JSON и ручная комбинация совпадают. |
| FLT-12 | P0 | Сначала поиск с keywords и географией A, затем новый поиск с другой географией B без keywords. Повторить вторым запросом `filters={}`. | Удалены прежние ключевые слова и фильтры, включая Exclude. Нет остаточного ограничения, не указанного в новом запросе. |
| FLT-13 | P1 | Для текстового фильтра передать заранее проверенное отсутствующее значение `QA_NONEXISTENT_{runId}`. | `FILTER_UNAVAILABLE` с названием фильтра/значением; нет выбора похожей подсказки, свободного тега вместо сущности без явного контракта или успешного ответа с неприменённым фильтром. |
| FLT-14 | P1 | На стенде задержать/перерисовать подсказки во время ввода Argentina; повторить на живом UI при естественной медленной загрузке. | Ввод не останавливается на `A`, не удваивается и не теряется после замены DOM-элемента. После выбора проверено конечное состояние. |
| FLT-15 | P1 | Выбирать географию при одновременно видимых Include, Exclude и похожих подсказках; отдельно воспроизвести случай, когда нужное слово есть в карточке результата. | Клик попадает в Include нужной подсказки нужного фильтра. Совпадение текста вне панели не даёт ложного успеха. |
| FLT-16 | P1 | Открыть панель фильтра заранее; повторить с закрытой панелью, подсказками вне fieldset и закрываемой подсказкой обучения. | Фильтр остаётся доступен в каждом поддерживаемом варианте. Повторный клик не закрывает уже раскрытую панель перед вводом; посторонняя подсказка не перехватывает действие. |
| FLT-17 | P1 | После ручного выбора A передать A повторно; отдельно передать массив `[A,A]` и пустые массивы фильтров. | Повторное значение не снимает выбор как переключатель. Пустые массивы не создают условий; `appliedFilters` описывает реальный конечный набор. |
| FLT-18 | P0 | На стенде сделать пункт кликабельным, но без применения фильтра, или добавить задержку обновления выдачи после выбора. | Коннектор не возвращает прежнюю выдачу с якобы применённым условием. Возвращает данные только после подтверждения фильтра и актуального результата либо явную ошибку. |

## 3. Карточки, объём выдачи и страницы — RES

Для постраничных кейсов подготовить Q1, фактический размер страницы N и ручной список URL. Не считать, что на странице всегда 25 результатов.

| ID | Приоритет | Предусловия и шаги | Ожидаемый результат |
|---|---|---|---|
| RES-01 | P1 | Получить 5 карточек; сопоставить name, title, company, location и ссылку с UI для каждой. | Поля относятся к одному человеку. Должность не включает имя компании, имя — степень связи, компания — стаж или соседнюю карточку. |
| RES-02 | P1 | В выдаче использовать карточки без должности/компании/географии и с длинными строками. | Отсутствующие данные представлены `null`; присутствующие извлечены без выдуманного заполнения. `rawText` не длиннее 2000 символов и относится к этой карточке. |
| RES-03 | P1 | На стенде добавить вложенные `li`, взаимные контакты, рекомендованные профили и несколько ссылок на человека с query/hash. | Одна запись на карточку/нормализованный URL; взаимные контакты и боковые рекомендации не становятся отдельными результатами основного поиска. Ссылки открывают нужного человека. |
| RES-04 | P1 | Выполнить Q2 с подтверждённым UI нулём результатов. | `people=[]`, `nextCursor=null`, `partial=false`. Ноль распознаётся только по явному состоянию пустой выдачи, без карточек от прошлого запроса. |
| RES-05 | P1 | На стенде показать загрузку, сбой сервера, paywall или пустой каркас вместо карточек. | Ни один из этих экранов не возвращается как успешные «0 результатов». Есть ошибка, отражающая причину, и доступная диагностика. |
| RES-06 | P0 | Для Q1 запросить `limit=1`, затем продолжить с возвращённым cursor. | RES-08 | P1 | Для Q3 запросить больше доступного количества. | Возвращены все доступные карточки, `requestedLimit` равен запросу, `nextCursor=null`, `partial=false`: естественный конец выдачи не является сбоем. |

## С чего начать

### Быстрый прогон чтения и preview

Последовательность: SES-02 → API-01 → API-08 → API-09 → FLT-02 → FLT-05 → FLT-11 → FLT-12 → RES-01 → RES-04 → RES-06 → PRF-01 → PRF-02 → DIA-02.

Этот прогон проверяет основной маршрут и несколько самых вероятных расхождений без реальной отправки. В API-09 проверяется запрещённый commit в review и preview в execute; переключать режим только при отсутствии других активных тестов.

### Перед включением отправок

На стенде пройти API-08/09, MSG-03/06/07, CON-05/08, OPS-01/02/04/05/06/07. Затем на согласованных получателях выполнить MSG-01, CON-01, CON-02 и подтвердить OPS-01 повтором уже выполненного действия. Прохождение только preview не является основанием считать браузерную отправку проверенной.

### После изменения селекторов

Повторить FLT-02/05/12/14/15/16/18, RES-01/03/06/07, PRF-01/02 и относящиеся к изменению MSG/CON. Для каждого сохранённого проблемного HTML полезен локальный регрессионный тест: точный элемент выбран, соседний Include/Exclude или чужой профиль не выбран. Статический HTML проверяет DOM-сопоставление, но не выполняет реальные серверные переходы.

## Шаблон результата и дефекта

Для каждого прогона создать отдельную копию [шаблона отчёта](test/manual/RUN-TEMPLATE.ru.md). Не менять ожидаемый результат ради совпадения с фактическим.

Минимальное доказательство FAIL: запрос + ответ + состояние UI + ожидаемое отличие. Для отправок добавить OP, снимок журнала, адресата и независимое подтверждение числа исходящих действий. Для ошибок страниц/фильтров приложить PNG/HTML с временем. При передаче отчёта за пределы проекта убрать личные данные из копий артефактов.

Критерий завершения: нет открытых P0 для используемых операций; основной набор P1 пройден на целевом аккаунте и языке; все BLOCKED/N/A имеют причину. Поддерживаемые варианты UI перечислены явно. Непроверенные отправки и дополнительные языки не объявляются работающими по результатам локальных модульных тестов.
